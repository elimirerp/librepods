# AirPods case discovery: stable identity and current BLE address

## Scope and provenance

Static Apple-code inspection, plus parent-reported outcomes. No account keys, Bluetooth writes, pairing changes or radio probes performed for this report. Identifiers and key values are deliberately absent.

Code provenance: retained official Apple OTA iOS26.7.1 build23H6030 Beta binaries. See CASE-IDENTITY-AND-OWNER-LINK.md for OTA URL and binary hashes. Extracted FindMyBluetooth framework SHA256: `0ec75f62aaa444968fe4c655543246085d6b7cd7533a2eb8c220207fdd9a68d3`. Framework disassembly uses `--force` because its dyld-cache external pointer destinations are outside the individually extracted image. Local code and Objective-C stub destinations are available; unresolved external Swift call targets must not be assigned guessed names.

## Current concrete case identity

The parent recovered the three records of the exact owned group, resolved the string separator issue (trailing section-sign character), and uniquely selected role/position2 as the case. Roles0/1/2 are distinct parts of the same group. Stable case beacon identity must be selected before generating address candidates; the audio Bluetooth identity and group UUID are separate fields.

Parent-reported live result: Android now returned an exact address match to the selected case, with RSSI -23. Private equality checks found the matched beacon UUID equal to the position2 case UUID and the address among that case's candidate set. The current case set has82 candidates over a plus/minus12-hour window. The reported observation index31 was subsequently reconciled privately to the primary chain at library branch index31. The sorted candidate ordinal was76 in the case-only file; those fields are distinct. A later live match followed rotation to primary observation index32.

This observation proves the selected case is currently reachable at an address generated by the existing rolling-key implementation. It does not prove every future advertising state uses that same address, that its current advertisement is type0x12, or that the target exposes FD44 before authorization. The callback had Apple manufacturer data but no parsed FindMy status; do not reject a privately exact-matched owned address solely because the advertisement parser does not classify it as type0x12.

## Verified native owner chain

1. `CLDurianDeviceManager didFetchAllDurians:` obtains `SPBeacon.simpleBeacon.identifier` at0x10146c6a0, uses it to fetch/create the local device at0x10146c6cc and sets the beacon at0x10146c6d8. GroupUUID and groupPartNumber are read separately at0x10146c6f4 and0x10146c720. See `didFetchAllDurians.asm`.
2. Factory0x10146e4cc selects CLHawkeyeDevice for accessory beacons and CLHeleDevice for Hele. The device-manager cache is keyed by beacon UUID. See `deviceWithUUID.asm`.
3. Owner connection material is requested by device UUID, not its cached audio CBPeripheral UUID: `SPBeaconManager connectionTokensForBeaconUUID:criteria:completion:` at0x10147b3e0. Normal owner criteria are drift-modeled; a reconciled scan can narrow them to matched sequence/index. See `fetchConnectionTokensDevice.asm`, `fetchConnectionTokens.asm` and `addScanResultAtDate.asm`.
4. `SPCommandKey.address` is exactly its beaconingKey.key bytes[0:6]. Mac SearchParty implementation0x1b878d304 calls beaconingKey/key/subdataWithRange:{0,6}, with no IRK transform. `SPCommandKeys.address`0x1b87bf060 does the same. Evidence: `work/sp-disassembly.txt` lines10447+ and63241+.
5. locationd copies the material address, and for FindMy-network devices ORs its first byte with0xc0 at0x10147ef08..0x10147ef10. It calls `CBCentralManager createPeripheralWithAddress:andIdentifier:nil` at0x10147f008; fallback formats a `Random ...` address and calls retrievePeripheralWithAddress. See `retrievePeripheralForMaterial.asm`. This is the BLE static-random public-key-prefix form, not an RPA derived from an IRK.
6. Connection token and primary/secondary indexes are copied from the native key object into CLFindMyAccessoryConnectionMaterial unchanged. The token is32 bytes; connection takes its first16 for CBConnectPeripheralOptionUseTempLTK. See `didFetchConnectionMaterial-full.asm` and CASE-IDENTITY-AND-OWNER-LINK.md. Temporary owner-link LTK is distinct from the fresh16-byte ranging-session IRK generated in nearbyd.

The native flow can construct the target peripheral from the derived address; it does not require FD44 to appear in an advertisement. A cached audio peripheral's service inventory therefore cannot identify the separate currently advertising case endpoint.

## Reconciled scan matching

`CLDurianDeviceManager addScanResultAtDate:address:advertisementData:...reconciledInformation:...` at0x1014727ac reads the reconciled UUID, resolves its existing device, stores the observed address in CLDurianScanCache, builds criteria from `sequence` plus `matchedIndex` (or matched primary indexes), then updates lastReconciledCriteria/address. If a connection is already being attempted or established and reconciliation changed, it refetches connection tokens using the narrowed criteria at0x101472a50. See `addScanResultAtDate.asm`.

`CLDurianMaintenance getAddressForDevice:`0x10149ea90 delegates to CLDurianScanCache.getAddressForUuid. The cache getter0x10149836c returns the `kCLScanResultAddressKey` stored under the stable UUID, not an unrelated Bluetooth audio address. See `getAddressForDevice.asm` (first15 instructions) and `scan-cache-address.asm`.

Thus a deterministic implementation has two checks: select exactly one owned case record; privately match an observed address to that record's generated address set. On a match, retain the exact candidate's key sequence/index metadata rather than assuming a list ordinal identifies the crypto index.

## Key-selection limits

The vendored FindMy implementation's current SKN/SKS candidate behavior and native relative-seed off-by-one convention are documented in INDEXED-INTERMEDIATE-KEY.md. Native indexed TimeBasedKey generation updates its supplied seed index+1 times before deriving `intermediate`; the native caller's supplied seed/time/index convention is still not mapped to the cloud fields. Do not change working live derivation based only on that relative-seed result.

`nearOwnerCommandKeysWithCompletion:` exists, but the inspected implementation constructs ordinary SPCommandKeys from TimeBasedKey intermediate/public material, including the same connect KDF. No verified finding establishes fixed secondary index0 or a special case-only nearOwner key policy. Extracts: `nearOwnerCommandKeys-trampoline.asm`, `nearOwnerCommandKeys-wrapper.asm`, `nearOwnerCommandKeys-native.asm`, `nearOwnerCommandKeys-tail.asm`, `nearOwnerCommandKeys-keyconstruction.asm`.

## Preserved alternate privacy-address path

There is a separate native IRK path; its applicability to this AirPods case is not established:

- FindMyBluetooth `Peripheral.pairingInfo` calls CBCentralManager.retrievePairingInfoForPeripheral at0x2522f4860, then obtains `kCBMsgArgRemoteAddress`, `kCBMsgArgRemoteAddressType`, and `kCBMsgArgRemoteIRK` from that local Bluetooth pairing dictionary at0x2522f4b74,0x2522f4bd8,0x2522f4c40. It constructs PeripheralPairingInfo(remoteAddress:remoteIRK:). This is existing Bluetooth pairing metadata, not a cloud-key KDF. See `FindMyBluetooth-pairinginfo-getter-head.asm`, `FindMyBluetooth-retrieve-pairinginfo.asm` and exported symbols in `FindMyBluetooth-ios26-symbols.txt`.
- FindMyBluetooth CBDiscovery.Config accepts OOBKeyInfo(btAddress,irkData). Native code creates CBOOBKeyInfo, sets IRK0x25232ae28, address0x25232ae58, addressType0x25232ae74, then passes the aggregated list to CBDiscovery.setOobKeys0x25232af14. See `FindMyBluetooth-material-conversion.asm`. DiscoveryTypes include findMyAccessory and proximityPairingBuffer.
- Peripheral.Options accepts pairingInfo and temporaryLTK separately; the framework imports CBConnectPeripheralOptionTemporaryIRKValue and TemporaryIdentityAddress as well as UseTempLTK. These are alternate privacy-address and link-authentication parameters, not evidence that a temporary ranging-session IRK can discover the case.
- Searchpartyd LocalFindableAccessoryRecord stores connectionMaterial {MACAddress address, Data irk}, P256PrivateKey and SymmetricKey256. Ordinary Hawkeye BeaconStore/SPCommandKey rolling P224 material is a separate route. SPPeripheralConnectionMaterial's exported ObjC fields are irkData, btAddressData, btAddressWithTypeData. See searchpartyd-ios26-swift.txt lines1821+,820+ and work/sp-disassembly.txt lines62688+.

No actual pairing dictionary, IRK, account key or token was read for this investigation. No entitlement bypass or restricted-controller call is proposed.

## Advertisement timing and missed scans

The analyzed native code does not establish AirPods Pro3 firmware advertisement cadence or the exact connected-owner transition between manufacturer types0x07 and0x12. Those decisions run in accessory/controller firmware. Type0x07 proximity-pairing and type0x12 FindMy classifications cannot substitute for an exact owned-key address match.

The parent identified Android foreground-only fine-location permission rejection during scans with zero Apple callbacks. Those scans are not evidence that the case was absent or that its address required IRK resolution. A later bounded scan found the exact owned case address. The observed first-miss/next-match timing alone does not justify inventing a15-second advertisement period.

## Next smallest step

Use the privately exact-matched case address and its matched candidate metadata for the already authorized bounded service inventory. Preserve the owned-case and candidate equality guards. If the case exposes FD44, the verified capability handshake can be evaluated; if it does not, record that service result and preserve the identity proof. An address match proves identity, not owner-link authorization or UWB readiness.
